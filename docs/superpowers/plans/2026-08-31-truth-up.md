# Truth-Up Pass Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make every public claim in this repository true, remove the documents not worth a stranger's time, and leave behind a committed audit a reader can re-run.

**Architecture:** Eight tasks. The first two carry the findings that outrank everything else — a public web root serving an uncorrected copy of the page being fixed, and a false security guarantee. The middle four correct claims surface by surface. The last two restructure the tree and produce the audit that proves the work.

**Tech Stack:** Markdown, Blade, CSS. No application logic changes except one Filament resource and `composer.json` metadata.

**Spec:** `docs/superpowers/specs/2026-08-31-truth-up-design.md`

## Global Constraints

- **Do not change behaviour to make a claim true.** This pass corrects documentation to match the code. The one exception is Task 5's Filament resource, which exists because the alternative is deleting a feature users may already depend on.
- **Never quote a value you are telling the project to remove.** The spec's own hard requirement 1 was briefly unsatisfiable because it quoted the IP it banned. Describe it.
- **Every claim you correct gets a row in the audit** (Task 7) with file, line, evidence, and verdict. A correction with no recorded evidence cannot be re-checked by a reader, which is the point of the exercise.
- The five open defects — D10, D12, D13, D15, D16 — are documented, not fixed.
- Do not touch `.env*`, and do not print the contents of any env file: they hold a live API key.
- A long benchmark run may be in progress against the `mnemon-full` Compose project. Do not disturb it or the unrelated `mnemon-pg` container.
- Both suites stay green: `php artisan test --compact` and `cd benchmark && python3 -m unittest discover -s tests -t .`.
- Run `./vendor/bin/pint` before committing anything touching PHP.

- `README.md` — "a project-specific agent sees only its own wing".

Replace each with what is true: wing restrictions constrain the **palace** layer, and the wiki layer has no wing dimension, so any token can read any wiki page.

`resources/views/mcp/authorize.blade.php` tells the user "Choose which wings this agent can see" at the moment they grant a token — the worst possible placement for an implication the wiki layer cannot honour. Reword so the user understands the restriction applies to palace content.

## Self-review

**Spec coverage.** Every section of the spec maps to a task: the public web root and fonts (1), the security guarantee (2), the landing page correction list (3), README/USERGUIDE/benchmark (4), authenticated views and metadata (5), the restructure, roadmap reconciliation and link integrity (6), the audit (7), the hard requirements (8).

**The plan's own risk.** Its failure mode is the spec's failure mode three times over: fixing what is enumerated and missing what is not. Task 7 exists to catch that, which is why it walks an enumerated universe rather than re-checking the correction list — a list-driven audit would find exactly what the list already knows.

**No placeholders.** Every task names files, and every verification step names a command with an expected result.
